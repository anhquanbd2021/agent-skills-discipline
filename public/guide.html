What each gate asks for

Every gate has an evidence contract — fields that must exist and be real, not just present. Inspired by the skill structure in addyosmani/agent-skills: process, rationalizations, verification.

1 · DEFINE — "Spec before code"

A spec with objectives and acceptanceCriteria — intent a reviewer can check. A title is not a spec; "make it better" is not a criterion.

Catches: no spec, hollow spec (objectives but no acceptance criteria), the "too small to need a spec" excuse.

2 · PLAN — "Small, atomic tasks"

A task list where every task carries its own verify step. A plan without a per-step check is a wish list.

Catches: no plan, tasks with no verify field.

3 · BUILD — "One slice at a time"

A bounded diff: ≤ 12 files, ≤ 400 insertions. The point isn't the exact numbers — it's that the change is small enough for a human to actually review.

Catches: monster diffs, missing file lists. Perfect paperwork does not excuse a 900-line blob.

4 · VERIFY — "Tests are proof"

A testReport with the command that ran and real counts (passed > 0, failed === 0). If the diff touches UI files (.html/.css/.jsx/...), a runtimeCheck with a tool and observations is required too.

Catches: missing reports, hollow reports (passed: true), failing suites, UI changes never seen running — and the "probably works" / "flaky" / "clicked through it" excuses.

5 · REVIEW — "Improve code health"

A securityScan (tool + findings list — an empty list is valid evidence, untriaged findings are not) and a non-empty selfReview checklist.

Catches: filled-but-hollow evidence — the "rationalized" agent submits a real scan and still fails, because findings were left untriaged while it claimed "low-risk, triage after merge."

6 · SHIP — "Faster is safer"

A release record: a prDescription a human can review, a rollback plan, and a docsNote (docs updated, or why none were needed).

Catches: unreviewable PRs, no rollback path, and "ship it now" pressure.

Honest limits

  • Presence ≠ truth. The engine checks that evidence exists and is well-formed — it cannot tell whether a test report is real. In the real world, CI produces the evidence; here, the fixture JSON does.
  • The scanner is a string match. It catches phrased excuses, not sophisticated ones — a model trained on the corpus could learn to phrase around it. Real anti-rationalization lives in the review culture, not the regex.
  • Markdown is persuasive, not enforced. The real Agent Skills pack is instructions an agent can still ignore — the lab models the ideal: a gate that cannot be talked past.
  • Thresholds are illustrative. 12 files / 400 insertions are teaching numbers, not universal limits — the actual pack argues for ~100-line reviewable changes.

This is an educational demo, not production infrastructure.
